k8 attempt 2 pre-registration (written before window open, 2026-11-02T15:59Z)
Change under test: software-pipelined (double-buffered) K loop in the 64x64 GEMM (gk.om gkgemm64,
gkld64, gksts64). Each K tile first issues the global loads of the next tile into staging registers
R142-157 (predicated @P1, P1 = ktiles left >= 2), runs its 64 FFMA steps from the current shared buffer,
then stores the staging into the other buffer (two 4352-byte buffers, 8704 bytes) behind one barrier;
k7b had two barriers per tile and exposed the global-load latency every tile. Registers 144 -> 168 (see attempt 1).
The 64x64 kernels move from ids 32..39 (one 16 KiB slot) to ids 40,42,..,54 (two slots each), because
the beta kernels are 17008 bytes. gpu-disasm.sh cuts two slots for ids 40-54.
Attempt 1 (window 20261102T153743Z-8dfb45, receipts /tmp/gk/k8/w) FAILED: every P and PT run printed
"GX 99 -110 42 3 0 0 1" (gkmm false, launch wait timeout -110 at the 5 s gkwait, 3 launches done) and
exited rc 84; B in the same window was healthy (t200-B T 9200 1508182, ck_after ec4a8c21...).
Root cause: the 64x64 kernels use R158 (buffer step) but declared gkgpr 160. Volta+ hardware burns
2 GPRs of the QMD count for the program counter (Mesa NAK sm70.rs:101 hw_reserved_gprs, api.rs:275
QMD count = num_gprs + 2), so R158/R159 lie outside the allocation. Same failure mode as gr.om's R69-R71
under 72 (evidence/OMEGALLM/geval/a1). Shared memory ruled out: QMD word 36 fixed bits 0x4B44800 give
MIN 9 / MAX 26 / TARGET 9 SM config (32 / 100 / 32 KiB, clcdc0qmd.h MW(1168:1163) etc.); 8704 fits.
Fix: put gkgpr id 168 for the 64x64 kernels; kernel code unchanged. Occupancy unchanged at 64
threads per block: floor(65536/(160*64)) = floor(65536/(168*64)) = 6 blocks per SM.
