k7 pre-registration (written before window open, 2026-11-02)
Change under test: register-bank remap and Ra operand reuse in the GEMM inner loops (gk.om 32x32
ids 0-7, 64x64 ids 32-39). Order note: the k6 README named fusion next and the k7 plan named the 128x128
retile; both are deferred because a cheaper defect sits under them: k6 FFMAs never set a reuse bit, and
in every k-step FFMA the b fragment (R36+j / R88+j / R104+j) and the accumulator (R16+4i+j / R16+8i+j)
share their low two register-index bits, so Rb and Rc collide in the published two- and four-bank
register-file models. sm_121's bank model is unpublished; this window measures it.
 OKBNK 1: C column j lives in accumulator column j xor 1 (gkcol), in the k loop and in both epilogues
   (gkacc32, gkacc64), so b and accumulator differ in the low two bits on every k-loop FFMA.
 OKREU 1: gkffma takes a reuse mask ru; the FFMAs of one row run carry Ra reuse (control bit 122) on
   j < last (3 of 4 in 32x32, 7 of 8 in 64x64), so each run's last FFMA releases it.
 Control bit 109: nvdisasm (CUDA 13.0 V13.0.88, -b SM121) decodes .reuse only when bit 109 (word-3
   bit 13) is also set, and ptxas 13.0 sm_121 emits all 49 .reuse instructions of a register-blocked
   probe kernel (/tmp/gk/k7/ru/r.cu) with it set (155 of 175 non-reuse instructions also set it). gkcw
   never sets it, so every k1-k6 instruction carries bit 109 clear. k7 sets it only on reuse FFMAs.
   Variant r0 therefore removes reuse and bit 109 together; the attribution is to the pair.
Exactness argument [INFERENCE until the run]: the remap renames registers and reuse/bit 109 are issue
hints; each C element's FFMA chain (operands, order, rounding) is unchanged from K6. K7, R0 and B0 are
predicted BIT-IDENTICAL to K6 on every output.
Variants (build.sh): r0 = OKREU 0 (remap only), b0 = OKBNK 0 (reuse only). Mutant t (OMUTT 0) kept:
it drops the k = 7 product of the thread's C element (row 0, column 0), now in register R17.
